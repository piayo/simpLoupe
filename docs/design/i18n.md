# 多言語化 (i18n) の設計

## 役割の違う2系統がある（統合しない）

翻訳データが2か所にあるが、**描画するのが誰かが違うため統合しない。**

| | (A) `src/i18n/ui/` → `src/ts/i18n.ts` | (B) `src/i18n/store/` → `src/_locales/` |
|---|---|---|
| 誰が描画するか | **拡張機能自身**。ルーペ内の設定パネルの DOM | **Chrome / ウェブストア** |
| どこに出るか | 設定パネルのラベルと選択肢 | ストアのページ、`chrome://extensions` の説明、ツールバーアイコンの tooltip、右クリックメニュー |
| 参照方法 | `T( "label.zoom" )` | `manifest.json` の `__MSG_xxx__` / `chrome.i18n.getMessage()` |
| 言語の解決 | 自前 (`pickLang()`) | Chrome がやる |
| キー | 意味的な ID（9キー） | `extDes` / `tglTtl`（2キー） |
| 言語コード | **BCP 47** (`zh-TW`, `pt-BR`)。「lang」と呼ぶ | **Chrome 形式** (`zh_TW`, `pt_BR`)。「locale」と呼ぶ |
| 未訳のとき | その言語の JSON を置かない → 実行時に `en` へフォールバック | `en` の文言で埋めたディレクトリを生成する |

> ⚠️ **この2つを混在させないこと。** 設定パネルの文言を `_locales` に移したり、
> `extDes` を `src/ts/i18n.ts` に入れたりしないこと。スクリプトも独立したパイプラインになっている
> (`scripts/i18n/check-ui.mjs` と `scripts/i18n/{build,check}-store.mjs`)。
> 用語 (lang / locale) も意図的に分けている。

分離はビルド後のバンドルでも成立している。`dist/js/content-script.js` には UI の訳が inline され、
`dist/js/service-worker.js` には**入らない**（`grep "倍率"` で 1 件 / 0 件・実測）。

### なぜ設定パネルの文言も `_locales` にしないのか

「9キーしかないのだから Chrome の i18n に全部乗せれば自前のパイプラインは不要」という案は却下した。
Chrome の messages.json のフォールバックは `<locale>` → 親 → **`default_locale`** の順で、
simpLoupe の `default_locale` は `ja`。**未訳の言語では UI が日本語で出てしまう。**
英語にフォールバックしたいので、UI 側は自前で持つ。

`default_locale` を `en` に変えれば解決するが、公開済みの拡張機能のストア掲載の既定言語が変わる副作用があり、
そのリスクは取らない（→ 「今後の判断事項」5）。

## 対応言語は35

`src/i18n/store/locales.json` の35ロケールが対象。姉妹プロジェクトの37ロケール
（Chrome がサポートするロケールから選んだ実績のあるリスト）から `en_GB` / `en_US` を削ったもの。
Chrome は `en_GB` → `en` と親にフォールバックするので `en` があれば同じカバー範囲になる。
（旧 `src/_locales/en_US/` は削除済み。`build-store.mjs` は余分なディレクトリを**自動で消さない**ので、
ロケールを減らしたときは報告を見て手で削除する）

`pt_BR` / `pt_PT` / `zh_CN` / `zh_TW` は Chrome の UI 言語がその形で来るので、素の `pt` / `zh` は作らない。

UI 側 (A) も同じ35言語を目標にする。BCP 47 表記なので `pt-BR` / `zh-TW` と書く。

**現時点で実際に訳があるのは `ja` と `en` だけ。** 残り33言語は後続フェーズ。
仕組みは言語数に依存していないので、`locales.json` と `messages.json` に行を足すだけで増やせる。

## A. 設定パネルの文言 — `src/i18n/ui/` → `src/ts/i18n.ts`

```
src/i18n/ui/
  keys.json      ← キー定義 (キー → 説明)。並び順 = このオブジェクトの並び順
  en.json        ← フォールバック先。**全キー必須**
  ja.json
  <lang>.json    ← 増やすときはここに追加

        │ import (tsconfig の resolveJsonModule)
        └──────────────▶ src/ts/i18n.ts（対応表 + T()。生成物ではない）
```

`src/ts/i18n.ts` は**生成物ではない。** 訳の JSON を import して並べた対応表と引き方だけを持つ。
言語を足すときは `import` と `transData` に1行ずつ足す。書き忘れは `npm run i18n:check:ui` が両方向で検出する。

### キーは英語の原文にしない

姉妹プロジェクトは英語の原文をキーにしており、「原文を1文字直すと全言語が黙って英語に戻る」という
構造的な弱点を抱えている（実際に `Loading` / `Now Loading` の事故が起きた）。
simpLoupe は最初から意味的な ID (`label.zoom`, `shape.round`) にしてこれを避けている。

代わりに「訳が無ければキーがそのまま出る」という暗黙の英語フォールバックが使えないので、
**`en.json` を実ファイルとして持ち、`FALLBACK_LANG = "en"` を明示している。**
`keys.json` の `fallbackLang` と `FALLBACK_LANG` のずれは `i18n:check:ui` が検出する。

### 言語の判定はブラウザの UI 言語

`chrome.i18n.getUILanguage()` を使う（content script でも権限なしで使える）。

**ページの `document.documentElement.lang` は見ない。** simpLoupe は任意のページに注入されるため、
`lang` が無いページが多く、また「英語のページを読んでいる日本語話者」に英語の UI を出してしまう。
（姉妹プロジェクトが `lang` を見ているのは、対象が単一のサイトだけで、そこには利用者の
アカウント言語が入るからで、simpLoupe には当てはまらない）

`pickLang()` は完全一致 → 地域コードを外す → 同じ言語の変種 → `FALLBACK_LANG` の順で解決する。
`zh-HK` / `zh-MO` は素の解決だと並び順で `zh-CN`（簡体字）を拾ってしまうため `LANG_ALIAS` で
`zh-TW` に読み替えている。

変種を選ぶ最後の行は `.toSorted()` ではなく **`.sort()`** を使っている。tsconfig の
`lib` が `ES2022` なので `.toSorted()` は TS2550 で型エラーになる。対象はスプレッドで複製した
配列なので破壊的ではない。oxlint の `unicorn/no-array-sort` はこの理由で off にしている。

### 未訳の言語は JSON を置かない

置くなら全キー揃えること（歯抜けは `i18n:check:ui` が error にする）。
置かなければ実行時に `en` へ落ちる。「置いたのに歯抜け」より「置いていない」ほうが状態が分かりやすい。

## B. Chrome が描画するテキスト — `src/i18n/store/` → `src/_locales/`

```
src/i18n/store/
  keys.json      ← キー定義 (description / maxLength / refs) と fallbackLocale
  locales.json   ← 生成するロケールの一覧。{ "ja": "Japanese" } のフラットな対応表
  messages.json  ← 翻訳文。{ "extDes": { "<locale>": "..." } } の表形式

        │ npm run i18n:build
        └──────────────▶ src/_locales/<locale>/messages.json  （生成物）
```

| キー | 上限 | 参照元 |
|---|---|---|
| `extDes` | 132文字（ストアの概要の上限） | `manifest.json` の `description` |
| `tglTtl` | 64文字 | `manifest.json` の `action.default_title` と `service-worker.ts` の `contextMenus.create` の**両方** |

`tglTtl` を tooltip とメニューで共有しているのは、文言が同じで片方だけ変えたい理由が無いため。
分ける必要が出たらキーを足す。

`manifest.json` の `name`（`"simpLoupe"`）は多言語化しない。固有名詞で全言語同一なので、
`__MSG_` 化しても35箇所に同じ文字列を並べるだけになる。

### 未訳のロケールも生成する（`en` で埋める）

ディレクトリを作らないと Chrome は `default_locale` = **`ja`** にフォールバックし、
フランス語圏の利用者に日本語の説明が出てしまう。英語で埋めたディレクトリを作るほうがマシ。

- `npm run i18n:build` が「未訳 N 件は `en` で代替」と報告する
- `npm run i18n:check:store` は未訳を **warn** として出す（`--strict` で失敗扱いになる）
- 訳が届いたら `messages.json` に1行足して `npm run i18n:build`

全言語の訳が揃ったら `--strict` を常用に切り替えるとよい。

### 決めたこと（姉妹プロジェクトから意図的に削ったもの）

| 姉妹プロジェクトにあるもの | simpLoupe で削った理由 |
|---|---|
| `gbl_dir`（文字表記の方向） | 35ロケールに RTL 言語が1つも無く、読む消費者もいない。あちらでも「誰も参照していない」死んだキーになっている |
| `icon_ttl`（拡張機能名の定数） | `name` を多言語化しない方針なので不要 |
| `kind: message / locale / constant` の分岐 | 全キーが `messages.json` 由来なので分岐が要らない |
| `keys.json` の `order` 配列 | オブジェクトの並び順を使う。並び順を二重に持つとズレる |
| `keys.json` の `groups` / `dynamic` | 変数経由で `T()` に渡す文言が無い |

**言語コードは変換しない。** UI 側は BCP 47、store 側は Chrome 形式のまま、それぞれのソースで
自然な形を使う。統一しようとすると2系統が混ざる元になる。

## 生成物を直接編集しないこと

| 生成物 | 編集すべき場所 | 生成コマンド |
|---|---|---|
| **`src/_locales/`** | `src/i18n/store/` | `npm run i18n:build` |

`src/_locales/` は見た目がふつうの手書きファイルなので特に注意。直接編集しても次の生成で黙って戻る
（`npm run i18n:check` が検出する）。ストア提出物なので `.gitignore` には入れず git で追跡する。

`src/ts/i18n.ts` は**生成物ではない**。訳の JSON を import して並べた対応表なので、
言語を足すときだけ `import` と `transData` に1行ずつ足す。

`npm run build` は i18n を**生成しない**（生成物を git 管理しているため、ビルドの副作用で
ソースツリーが書き換わるのを避けている）。ずれは CI の `i18n:check` が検出する。

## コマンド

| コマンド | 内容 |
|---|---|
| `npm run i18n:build` | `src/i18n/store/` から `src/_locales/` を生成 |
| `npm run i18n:verify` | 生成物が単一ソースとずれていないかだけを見る（速い） |
| `npm run i18n:check` | 下の2つをまとめて実行。**CI で回す** |
| `npm run i18n:check:ui` | `T()` 呼び出しとキー定義の突合、対応表のずれ、ロケールごとの過不足 |
| `npm run i18n:check:store` | 未訳・上限超過、`__MSG_` と `getMessage()` の突合、生成物のずれ |

CI は `i18n:check` 1本でよい（`check:store` が生成物のずれ検査を内包している）。
`--strict` は使わない。使うと未訳33言語で常に赤になる。

## 翻訳を編集する

| 編集したいもの | 編集する場所 | そのあと |
|---|---|---|
| 設定パネルの文言 | `src/i18n/ui/<lang>.json` | 何もしなくてよい（直接 import している） |
| 説明文・tooltip・メニュー名 | `src/i18n/store/messages.json` | `npm run i18n:build` |
| キーを増やす | 各系統の `keys.json` | 参照するコードも書く（未使用キーは error） |
| 言語を増やす (A) | `src/i18n/ui/<lang>.json` を追加 | `src/ts/i18n.ts` に import と `transData` を1行 |
| 言語を増やす (B) | `src/i18n/store/messages.json` に訳を追加 | `npm run i18n:build` |

## 今後の判断事項

1. **残り33言語の訳出。** 仕組みは出来ているので、`messages.json` と `src/i18n/ui/<lang>.json` を
   埋めるだけ。翻訳 API（DeepL / Google 翻訳）は使わない方針（外部サービスの契約と鍵の管理を増やしたくない）。
   人か AI が書き、仕組みが担保するのは「抜けを見逃さないこと」だけ。
2. **`extDes` の文言そのもの。** 現在の ja「シンプルなルーペ(拡大鏡)ツール。」/ en「Just the Simple Loupe Tool.」は
   旧 `src/_locales/` からそのまま移設したもので、132文字の枠に対してかなり短い。ストア掲載文の改善は別タスク。
3. **`shape` の値 `"quare"`（`square` の綴り間違い）。** UI キーは正しい綴りの `shape.square` にし、
   **表示ラベルだけ「四角 / square」に直して、`value="quare"` は据え置いた。**
   `chrome.storage.local` に保存済みの設定と `src/ts/types.ts` の `Config` 型がこの値に依存しているため、
   値を直すにはマイグレーション（`service-worker.ts` の `getConfig` で `quare` → `square` に書き換える処理）が
   必要で、i18n の作業とは切り離すべきと判断した。**キーと値が一致しないことは
   `src/i18n/ui/keys.json` と `element.ts` にコメントで明記してある。**
4. **35ロケールを英語で埋めたことが、ストア掲載上どう見えるかは未確認。**
   Chrome ウェブストアの「対応言語」表示はデベロッパーダッシュボードの掲載情報のローカライズで決まり、
   `_locales` では決まらない、という理解で35ロケール生成を選んでいるが、**確証は無い（未検証）。**
   もし `_locales` が「35言語対応」として表示されるなら、中身が英語なので誇大表示になる。
   次回のストア審査提出前にダッシュボードのプレビューで確認すること。
   気になる場合は `locales.json` を `ja` / `en` の2件に減らして `npm run i18n:build` を回すだけで戻せる。
5. **`default_locale: ja` を据え置いた副作用は未検証。** 「`en` に変えるとストア掲載の既定言語が変わる」
   という前提で `ja` 据え置き + 35ロケール生成を選んだが、**この副作用の存在自体を検証していない。**
   もし副作用が無いなら `default_locale: en` + `ja` / `en` の2ロケールという、はるかに小さい構成が正解になる。
   4 と合わせて、次にストアの設定を触るときに実物で確かめる。
6. **全言語が揃ったら `check:store --strict` を常用にする**（未訳を error に昇格させる）。
